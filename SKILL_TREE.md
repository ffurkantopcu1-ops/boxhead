# SKILL_TREE.md — Node trees (main wheel + ascendancy)

Two Path-of-Exile-style node trees drive per-run character power. Both are
**data-driven and GENERATED** — edit the generator + theme tables and regenerate,
don't hand-edit the JSON. Turkish is the UI language; identifiers are English.

## Two trees

1. **Main passive tree** — a large ~234-node **wheel**, allocated with Skill
   Points (`player.skill_points`, +1 per level). Available from level 1.
2. **Ascendancy tree** — a small **subclass** mini-tree that *opens at level 20*
   when you pick one of your class's 2 evolutions. Allocated with a separate
   currency, **Ascendancy Points** (`player.ascendancy_points`, +1 per level
   from level 20 onward).

Both are **run-scoped** (live on the player, reset each run; not in `meta.json`),
**deterministic**, and **pathed** (a node is takeable only if it's a start node
or shares an edge with an already-allocated node).

## Tree 1 — Main passive wheel

**Generated by `tools/generate_skill_tree.py`** → `data/skill_tree.json`
(~234 nodes: 9 start, 9 keystone, 45 notable, 171 minor). Canvas ≈ 3000×2600
(center 1500,1300, outer ring r≈1180). The UI **pans (drag) and zooms (wheel)** —
`scenes/game_scene.py draw_skills_tab` + `_skill_tree_transform`; it does **not**
fit one screen.

### Topology (a wheel, not hub+arms)
- **Inner ring (r≈240):** the 9 class **start** nodes evenly spaced at 40°
  (`CLASSES` order in the generator), interleaved with 9 generic **junction**
  minors (`arm:"core"`). Ring closes start → junction → next start.
- **Class sectors:** each class radiates **3 rails (L/C/R)** outward through
  **6 rings**, with tangential rungs (L–C–R) at each ring. The **keystone** sits
  at the C-rail tip; **notables** at C-rail rings 2 & 4 and the L/R-rail tips.
- **Bridges:** between neighbouring classes, a 6-ring generic **bridge** rail
  (`arm:"core"`) with cross-class rungs (`<cls>_R{k} ↔ bridge ↔ <nxt>_L{k}`),
  so you can walk from one class's sector into a neighbour's — expensively.

No single "center" node; shared/generic power lives on the ring junctions and
bridges (`arm:"core"`, ~63 nodes total). Scarcity (a normal ~20–30 SP run affords
~10% of the graph), not walls, keeps builds distinct.

### Node schema (`data/skill_tree.json`, emitted by the generator)
```jsonc
{
  "id": "warrior_C4",              // <start_cls> | junc_<cls>_<nxt> | <cls>_<rail><k> | bridge_<cls>_<nxt>_<k>
  "name": "🏰 Siper", "desc": "+80 Can, +12 Zırh",
  "arm": "warrior",               // a class id, or "core" (junctions/bridges)
  "type": "minor|notable|keystone|start",
  "start": true,                  // only present on the 9 start nodes
  "stats": { "max_hp": 80, "armor": 12 },   // summed into recalculate_stats
  "connects": ["warrior_C3"],     // edges declared once (engine builds symmetric adjacency)
  "pos": [x, y]                    // wheel canvas coords
}
```
`stats` keys must be ones `InventoryManager.recalculate_stats` sums (max_hp,
dmgMult, armor, speed, critChance, critDmg, attack_speed_bonus, lifesteal,
physDmgFlat, fireDmgFlat, frostDmgFlat, elementDmgMult, dotDmgMult, poisonDps,
aoe_bonus, pierce, bounce, bullet_speed, turretDmg/Rate/MaxHp/Limit,
minionDamage/Count/Rate/MaxHpFlat, meleeRangeFlat, dodgeChance, regen, …).
Keystone downsides use `max_hp_pct` (e.g. `{"dmgMult":0.30,"max_hp_pct":-15}`)
or a negative multiplier — every keystone carries a real cost (`AGENTS.md`).

### Content contract
Per-class flavour lives in the generator's `THEMES` table (each class: a 5-minor
rotating pool, 2 notables, 1 keystone); junctions/bridges draw from `GENERIC` /
`GENERIC_NOTABLES`. **To change the tree, edit the generator + tables and re-run
`python tools/generate_skill_tree.py`.** The JSON is a build artifact.

## Tree 2 — Ascendancy (subclass)

**Generated by `tools/generate_ascendancy.py`** → `data/ascendancy.json`
(90 nodes = 18 subclasses × 5: a start + 2 minors + 1 notable + 1 keystone).
One tree per evolution in `Player.EVOLUTIONS`. All subtrees share one coordinate
space (only the player's chosen subclass is shown at a time).

- **Opens at level 20:** `Player.apply_evolution(evo_id)` calls
  `Ascendancy.seed_start(player)`, which auto-allocates that subclass's start
  node (`<evo_id>_a0`). The evolution's own stat+passive is the start's effect;
  the mini-tree adds allocatable subclass nodes on top.
- **Currency:** `player.ascendancy_points`, +1 per level from level 20
  (`entities/player.py _apply_level_gain`).
- **UI:** the **YÜKSELİŞ** inventory tab (`draw_ascendancy_tab`) — locked message
  before evolution, the subclass diamond after.

## Engine

`logic/skill_tree.py` (`SkillTree`) and `logic/ascendancy.py` (`Ascendancy`) are
stateless singletons (data + rules at class level). Per-player state is two sets
on the player: `allocated_nodes` and `ascendancy_nodes`.

Shared API shape: `is_allocatable(id, allocated)`, `allocate(player, id)`,
`refund_all(player)`, `resolve_stats(allocated)` → stat dict (summed in
`recalculate_stats` beside the card pool), `start_nodes_for/start_for`, and
module-load validation (unique ids, edges resolve, one start per arm/subclass,
starts reach a core node). `Ascendancy.allocate` additionally gates on
`player.evolution` (you can only allocate your chosen subclass).

## Save integration (`logic/save_manager.py`)
Persisted in the run save (not meta): `allocated_nodes`, `ascendancy_nodes`,
`ascendancy_points`. Old saves without them: seed start nodes; the pre-tree flat
`skills` levels are converted once to refunded SP so nothing is lost.

2. `python -m pytest tests/test_skill_tree.py tests/test_ascendancy.py -v`
   (pathing, allocation/points, stat resolution, data integrity, save round-trip).
3. `tests/test_class_balance.py` + `tests/test_lategame_balance.py` guard that
   fully-invested tree+ascendancy builds stay within the `AGENTS.md` power budget.
